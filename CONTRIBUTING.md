# Contributing

Thanks for helping keep OpenCode Model Guide accurate. The project is intentionally small and fully
static: changes should fit an existing slice, pass the quality gate, and avoid adding runtime
infrastructure.

## Pick and claim a slice

[`docs/slices/README.md`](docs/slices/README.md) is the single source of truth for status. Do not
invent a new feature outside the tracker.

1. Pick a `todo` slice or ask the owner before reopening a `done` one.
2. Claim it in the tracker: set status to `in-progress`, add your name, branch, and the claim date in
   the progress log.
3. Create a branch from `main`:

   ```bash
   git switch main
   git pull --ff-only
   git switch -c slice/SXX-short-name
   ```

4. Read the slice file and the design sections it references before editing.
5. Commit the claim separately, for example `docs: claim S11`.

When the work is ready, set the slice to `review`, open a pull request, and link the PR in the
tracker. Merge only after CI is green and the slice’s acceptance checklist is complete.

## Development rules

- **Tests first for logic.** Classification, scoring, event IDs, parsing, filtering, link resolution,
  and notification state all need tests.
- **Fixtures, not network.** Unit tests must not call live sources. Add a trimmed real payload to
  `packages/*/test/fixtures/` and test the parser against it.
- **No new runtime dependency without a reason.** Prefer the standard library and existing packages.
  Keep the site static; no database, server, analytics, or client-side data fetching.
- **Keep free labels separate.** Never infer `free` from a `-free` suffix. Never collapse the five
  labels into one score or badge.
- **Keep provenance.** New displayed values need a source, date, and confidence or a clear
  “insufficient data” state.
- **Accessibility is part of done.** Use semantic headings, labels, table captions, visible focus,
  text equivalents for visual state, and respect `prefers-reduced-motion`.

## Schema freeze

`SCHEMA_VERSION` in `packages/shared/src/schema.ts` is **1**. Do not change an existing field’s
meaning or remove a field in a normal PR.

A schema change requires:

1. a note in the relevant slice or a new tracker note explaining why the old shape is insufficient;
2. a version bump and migration path for committed snapshots;
3. updated Zod schemas, TypeScript types, fixtures, validation, and UI consumers;
4. a PR description that calls out the migration explicitly.

If you only need a new optional field, add it without breaking existing data, update the schema and
fixtures, and explain the addition in the PR.

## Data files

Generated files are committed for reproducibility and to keep the daily workflow alive:

| File | Generated by | Hand-edit? |
|---|---|---|
| `data/snapshot.json` | `pnpm ingest` | No |
| `data/history/*.json` | `pnpm ingest` | No |
| `data/events.jsonl` | `pnpm ingest` (append-only) | No |
| `data/benchmarks.json` | `pnpm score` | No |
| `data/scores.json` | `pnpm score` | No |
| `data/notify-state.json` | `pnpm notify` | No |
| `data/aliases.json` | Maintainer | **Yes** |

To change generated data, fix the adapter or source mapping and rerun the pipeline. To add a
benchmark alias, edit `data/aliases.json`, add a test, and explain the evidence in the PR.

Never commit `.secrets`, `.env`, API keys, or an ntfy topic. The workflow reads repository secrets;
it never reads a committed file.

## Quality gate

Run all of this before opening a pull request:

```bash
pnpm typecheck
pnpm test
pnpm validate:data
pnpm build
pnpm tsx scripts/check-links.ts
```

For a production-base check:

```bash
SITE_URL=https://cjrutherford.github.io BASE_PATH=/opencode-model-guide pnpm build
BASE_PATH=/opencode-model-guide pnpm tsx scripts/check-links.ts
```

If you changed a page, also check it at **360 px**, **768 px**, and **1280 px**; tab through every
control; and confirm there is no horizontal page scroll. If you changed the model table, detail page,
or compare flow, do a screen-reader pass on the table headers and heading order.

## Commit and PR style

Use conventional, imperative commit subjects:

```text
feat: add compare view
fix: keep base path on feed links
docs: claim S11
ci: add link check after build
```

Keep the claim, implementation, and tracker-link commits separate when practical. A PR should
contain one slice, a short summary, a verification section with real commands, and known limitations.

PR checklist:

- [ ] Slice claimed in the tracker and status set to `review`.
- [ ] Scope stays inside the slice’s files.
- [ ] Tests added or updated for behavior changes.
- [ ] `pnpm typecheck && pnpm test && pnpm validate:data && pnpm build` passes.
- [ ] Link check passes, including the production base path if links changed.
- [ ] Accessibility checks pass for changed pages.
- [ ] No secrets, generated noise, or unrelated files.
- [ ] Tracker progress log records the PR and CI result.
- [ ] Acceptance checklist is complete or the deferred items are explicit.

## Adding a source

A new source is not a drive-by adapter. It needs a design note covering its URL, cadence, fields,
authority, failure policy, legal terms, and name-resolution behavior. Add fixtures, tests, and a
`/health` row, then update [`docs/sources.md`](docs/sources.md). If the source is optional, make the
failure path explicit and keep the rest of the site deployable.

## Questions

Open an issue with the source URL, a sample payload or screenshot, and the date you observed it.
Source markup changes are expected; the fix is a fixture-backed adapter change, not silently
disabling the source.
